# XuiFactor Web Panel

پنل تحت وب برای [XuiFactor](https://github.com/PdYrust/XuiFactor) (ضریب مصرف ترافیک برای 3x-ui 3.x).
موتور اصلی همان باینری رسمی `xui-factor` است؛ پنل فقط یک لایه‌ی مدیریتی روی آن است و تمام تغییرات از طریق خود CLI رسمی انجام می‌شود.

## نصب

```sh
unzip xui-factor-panel.zip && cd xui-factor-panel
sudo ./install.sh
```

اسکریپت به ترتیب: نصب xui-factor + سرویس systemd، نصب فایل‌های پنل، و در پایان می‌پرسد «پنل وب می‌خواهی؟ (y)».
در صورت پاسخ y: پورت (پیش‌فرض `909`) ← نام کاربری/رمز (رمز خالی = ساخت خودکار) ← «دامنه داری؟»

* **دامنه دارم (y)** ← دامنه را می‌پرسد ← «پورت 80 باشد؟» (پیش‌فرض 80، قابل تغییر) ← SSL لتس‌انکریپت.
* **دامنه ندارم** ← گواهی SSL برای IP سرور (پروفایل shortlived، حدود ۶ روز، تمدید خودکار).

نصب بدون پرسش:

```sh
sudo ./install.sh --yes --port 909 --username admin --password 'Pass#1234' --domain panel.example.com --acme-port 80
sudo ./install.sh --yes --ip-cert        # SSL روی IP
sudo ./install.sh --yes --no-ssl         # بدون SSL (HTTP)
sudo ./install.sh --yes --no-web         # فقط xui-factor
```

## نصب با یک خط (پس از انتشار روی GitHub)

```sh
bash <(curl -Ls https://raw.githubusercontent.com/Mrignored/xpf/main/install.sh)
```

همین دستور آخرین Release مخزن را دانلود و نصب می‌کند و در پایان می‌پرسد «پنل وب می‌خواهی؟». گزینه‌ها هم پشت همین دستور کار می‌کنند، مثلاً:
`bash <(curl -Ls …/install.sh) --yes --port 909 --username admin --password 'Pass#1234' --domain panel.example.com`
(نسخه‌ی مشخص: `--version v1.1.0`).

## انتشار پروژه روی GitHub (فقط بار اول)

1. در github.com یک مخزن **Public** بسازید (مثلاً `xui-factor-panel`).
2. روی سیستم خود: `git clone https://github.com/USER/REPO.git`، سپس **همه‌ی فایل‌های این پروژه** (حتماً پوشه‌های `vendor/` و `.github/`) را داخلش کپی کنید.
3. مخزن خودتان را در پروژه ثبت کنید: `bash tools/set-repo.sh USER/REPO` (خط `XFP_REPO` بالای `install.sh` و آدرس‌های README را عوض می‌کند. روی ویندوز همین دو جا را دستی ویرایش کنید).
4. `git add -A && git commit -m "v1.1.0" && git push -u origin main`
5. `git tag v1.1.0 && git push origin v1.1.0` ← اکشن `release.yml` خودکار یک Release می‌سازد. (اگر Actions غیرفعال بود: GitHub ← Releases ← Draft a new release ← تگ را انتخاب و Publish.)
6. دستور یک‌خطی بالا را با USER/REPO خودتان اجرا کنید.

> فایل `vendor/*.tar.gz` (باینری xui-factor، حدود ۵ مگابایت) باید در مخزن کامیت شود؛ نصب‌کننده به آن نیاز دارد.

## بروزرسانی روی سرور

* **از پنل**: داشبورد ← کنار «نسخه پنل» دکمه‌ی «بررسی بروزرسانی». اگر نسخه‌ی جدید باشد بنر «نسخه‌ی جدید vX منتشر شده است» با دکمه‌ی «بروزرسانی به این نسخه» نشان می‌دهد؛ تأیید کنید تا نصب شود (پنل چند ثانیه ری‌استارت و صفحه خودکار رفرش می‌شود).
* **از ترمینال**: `xfp update` (می‌پرسد «Update to release vX? [y/N]»)، `xfp update --check` فقط بررسی، `xfp update --yes` بدون پرسش.
* **بدون GitHub**: `xfp update --archive release.tar.gz` (یا `.zip`) از فایل محلی.
* قبل از بروزرسانی بکاپ فاکتور گرفته می‌شود و نسخه‌ی قبلی در `/opt/xui-factor-panel.bak` می‌ماند. اگر نسخه‌ی جدید درست بالا نیاید **خودکار به نسخه‌ی قبل برمی‌گردد**. تنظیمات، رمز، گواهی SSL، دیتابیس و ضریب‌ها دست نمی‌خورند؛ حذف قبلیِ فقط-پنل-وب هم حفظ می‌شود.
* موتور xui-factor فقط وقتی نسخه‌ی همراه release با نسخه‌ی نصب‌شده فرق کند عوض (و ری‌استارت) می‌شود.
* منبع بروزرسانی (مخزن) هنگام نصب از GitHub خودکار ذخیره می‌شود؛ اگر از زیپ نصب کرده‌اید: `xfp set-repo USER/REPO`.
* **امنیت**: بروزرسانی کدِ مخزن شما را با دسترسی root اجرا می‌کند؛ پس روی حساب GitHub احراز هویت دومرحله‌ای بگذارید و فقط خودتان push کنید.

## زبان

رابط وب فارسی و انگلیسی است؛ دکمه‌ی کره‌ی زمین در منوی کناری (و صفحه‌ی ورود) زبان را عوض می‌کند و انتخاب شما ذخیره می‌شود. پیام‌های سرور هم به همان زبان می‌آیند. دستورات ترمینال (`xfp`) انگلیسی هستند.

## دستور `xfp` (همه‌ی امکانات پنل در ترمینال)

`sudo xfp` منوی تعاملی را باز می‌کند. دستورات مستقیم:

| دستور | کار |
|---|---|
| `xfp status` | وضعیت، تعداد قانون‌ها، ترافیک اضافه‌ی اعمال‌شده |
| `xfp set-inbound 1.5 3 4` | ضریب 1.5 برای کل اینباند 3 و 4 |
| `xfp remove-inbound 3` | حذف ضریب اینباند |
| `xfp set-client user@x 3 1.5` | ضریب کلاینت (ایمیل، شناسه اینباند، ضریب) |
| `xfp remove-client a b c` | حذف ضریب چند کلاینت |
| `xfp inbounds` / `xfp clients -q mail --page 2` | لیست با صفحه‌بندی و جستجو |
| `xfp events` | بررسی رویدادها (`--kind all` برای اعمال‌های ترافیکی) |
| `xfp clear-all` | پاکسازی کل ضریب‌ها |
| `xfp events-prune` | حذف رویدادهای تکراری «ثبت خودکار ردشد» |
| `xfp disable` / `xfp enable` | غیرفعال/فعال‌سازی کلی فاکتور |
| `xfp purge` | حذف فاکتور از دیتابیس + حذف سرویس |
| `xfp backup [--history\|--full]` | بکاپ فاکتور (کوچک) یا کل دیتابیس 3x-ui؛ مسیر ذخیره را چاپ می‌کند |
| `xfp backups` | فهرست بکاپ‌ها + مسیر پوشه‌ها |
| `xfp restore [فایل\|latest]` | بازیابی (بدون آرگومان: فهرست شماره‌دار و انتخاب) |
| `xfp backup-delete فایل` | حذف یک بکاپ |
| `xfp doctor`, `xfp cleanup` | بررسی سلامت / پاکسازی متادیتا |
| `xfp web-setup` | اجرای دوباره‌ی تنظیم پنل (پورت/یوزر/SSL) |
| `xfp credentials` | تغییر نام کاربری/رمز پنل |
| `xfp set-port N` | تغییر پورت پنل |
| `xfp ssl-issue [--domain D \| --ip]` | گرفتن گواهی |
| `xfp ssl-renew` | تمدید: دامنه را می‌پرسد و تمدید می‌کند |
| `xfp panel start\|stop\|restart\|status\|logs` | کنترل سرویس پنل |
| `xfp update [--check\|--yes\|--archive F]` | بررسی و نصب آخرین Release |
| `xfp set-repo USER/REPO` | مخزن GitHub منبع بروزرسانی |
| `xfp uninstall --web-only` | حذف فقط پنل وب؛ xui-factor و ضریب‌ها ادامه می‌دهند |
| `xfp uninstall --all` | پایان پروژه: بکاپ خودکار ← حذف رکوردهای فاکتور از دیتابیس ← حذف سرویس و باینری و پنل |

## امکانات پنل

* **داشبورد**: تعداد ضریب اینباند/کلاینت، کلاینت‌های دارای ضریب، دفعات اعمال، حجم اضافه‌ی محاسبه‌شده (کل و ۲۴ ساعت)، آخرین اعمال، رویدادهای اخیر.
* **ضریب اینباندها**: ثبت با شناسه‌ی اینباند، ویرایش، حذف، انتخاب چندتایی و ثبت/حذف گروهی، جستجو و صفحه‌بندی.
* **ضریب کلاینت‌ها**: ثبت با ایمیل (+ شناسه‌ی اینباند)، ویرایش، حذف، انتخاب چندتایی (حتی بین صفحه‌ها)، فیلتر (دارای ضریب/اختصاصی/اینباند/بدون ضریب)، جستجو، صفحه‌بندی.
* **بررسی و گزارش**: رویدادهای مدیریتی و اعمال ترافیک با فیلتر، جستجو و صفحه‌بندی.
* **نگهداری**: غیرفعال/فعال‌سازی کلی، پاکسازی کل ضریب‌ها، doctor/backup/cleanup، **حذف کامل فاکتور از دیتابیس** (جدول‌های `xui_factor_*` + سرویس؛ با تأیید تایپ `DELETE` و بکاپ خودکار).
* **بکاپ و بازیابی**: ساخت بکاپ فاکتور و بکاپ کامل دیتابیس، دانلود روی سیستم شما، حذف، و بازیابی با انتخاب فایل یا درگ‌ودراپ. مسیر ذخیره روی سرور در خود صفحه نوشته شده است (جزئیات پایین).
* **حذف پنل وب** (در «نگهداری و حذف»): فقط پنل، یا حذف کامل پروژه از سرور (پس از غیرفعال‌سازی و پاک‌کردن رکوردهای دیتابیس).
* **حساب کاربری**: تغییر نام کاربری و رمز.
* **بروزرسانی**: بررسی نسخه‌ی جدید از GitHub و نصب با یک کلیک.
* **زبان**: فارسی و انگلیسی.
* **تم**: روز و شب مثل 3x-ui (دکمه‌ی خورشید/ماه در منوی کناری؛ انتخاب شما ذخیره می‌شود).

## رفتار ضریب‌ها (مهم)

* در 3x-ui 3.x یک کلاینت می‌تواند به چند اینباند وصل باشد و موتور هر کلاینت را یک‌بار ضریب می‌دهد. اگر برای دو اینباندِ دارای کلاینت مشترک ضریب بگذارید، دومی بی‌اثر است و فقط رویداد تکراری می‌سازد؛ پنل (از نسخه‌ی 1.2.0) چنین ثبتی را رد می‌کند و ضریب‌های بی‌اثرِ قبلی را با برچسب «بی‌اثر (هم‌پوشان)» نشان می‌دهد. رویدادهای تکراریِ قبلی را از «نگهداری و حذف» یا `xfp events-prune` پاک کنید.

* ضریب ≥ 1 است (`1.5` یعنی ترافیک جدید ۱۵۰٪ حساب شود). این محدودیت خود موتور xui-factor است.
* ضریب اینباند روی همه‌ی کلاینت‌های اینباند و کلاینت‌های جدید اعمال می‌شود. تغییر آن، ضریب قبلی را جایگزین می‌کند (نه اینکه روی هم انباشته شود).
* ضریب کلاینت از ضریب اینباند اولویت دارد. اگر کلاینتی زیر ضریب اینباند باشد، ضریب اختصاصی او به‌صورت *override* ثبت می‌شود؛ با حذف آن، کلاینت به ضریب اینباند برمی‌گردد.
* حذف ضریب اینباند، ضریب‌های اختصاصی کلاینت‌های همان اینباند را حفظ می‌کند (پنل بعد از حذف دوباره اعمالشان می‌کند، چون دستور `disable-all --inbound-id` خود موتور آن‌ها را هم خاموش می‌کند).
* غیرفعال‌سازی ضریب، ترافیک قبلاً ضریب‌خورده را برنمی‌گرداند.
* قبل از هر حذف/تغییر، یک `tick` اجرا می‌شود تا مصرف معلق از دست نرود.
* «غیرفعال‌سازی کلی» = pause همه‌ی قانون‌ها + توقف سرویس؛ «فعال‌سازی» = روشن کردن سرویس + resume از شمارنده‌ی فعلی.

## بکاپ و بازیابی

| نوع | چیست | مسیر روی سرور |
|---|---|---|
| **بکاپ فاکتور** | فقط جدول‌های `xui_factor_*` (ضریب‌ها و مبنای مصرف)، فشرده `.db.gz`، معمولاً چند کیلوبایت | `/var/backups/xui-factor-panel/` |
| **بکاپ کامل** | کپی کل دیتابیس 3x-ui (فاکتور هم داخلش هست) با دستور رسمی `xui-factor backup` | `/var/backups/xui-factor/` |

* دانلود: از صفحه‌ی «بکاپ و بازیابی». آپلود/بازیابی: همان صفحه (درگ‌ودراپ یا انتخاب فایل) یا `xfp restore`.
* **انتقال به سرور دیگر**: (۱) 3x-ui و دیتابیسش را در سرور جدید بالا بیاورید، (۲) `install.sh` را اجرا کنید، (۳) بکاپ فاکتور را بازیابی کنید. کلاینت‌ها با **ایمیل** تطبیق داده می‌شوند، پس شناسه‌ها می‌توانند فرق کنند؛ کلاینتی که در سرور جدید نیست نادیده گرفته می‌شود و هشدار می‌دهد.
* با گزینه‌ی پیش‌فرض «بازنشانی مبنای مصرف»، ضریب فقط روی ترافیکِ بعد از بازیابی اعمال می‌شود (ترافیک گذشته دوباره ضرب نمی‌شود).
* قبل از هر بازیابی و هر حذف کامل، خودکار یک بکاپ از وضعیت فعلی گرفته می‌شود (`…-pre-restore` / `…-pre-purge`). بازیابی فقط جدول‌های فاکتور را عوض می‌کند، نه جدول‌های 3x-ui.
* بکاپ کامل فقط دانلود می‌شود؛ بازیابی‌اش دستی است (جایگزینی فایل دیتابیس با توقف x-ui).
* برای جلوگیری از پر شدن دیسک، حداکثر ۳۰ بکاپ فاکتور نگه داشته می‌شود. حذف پنل/فاکتور هیچ‌وقت بکاپ‌ها را پاک نمی‌کند.
* پیش‌فرض بکاپ، تاریخچه‌ی اعمال ترافیک را شامل نمی‌شود (حجم زیاد)؛ با گزینه‌ی «شامل تاریخچه» یا `--history` می‌آید.

## مصرف منابع

* پنل یک پروسه‌ی پایتون بدون وابستگی است: حدود ۲۰ تا ۳۰ مگابایت RAM و CPU تقریباً صفر در حالت بیکار. سرویس systemd آن سقف دارد: `CPUQuota=25%`، `MemoryMax=128M`، `Nice=10`، اولویت I/O پایین.
* دیتابیس فقط خوانده می‌شود (حالت read-only)؛ آمار سنگین (جمع حجم اضافه از رویدادها) ۶۰ ثانیه کش می‌شود و داشبورد هر ۳۰ ثانیه (و فقط وقتی تب باز و فعال است) بروز می‌شود. صفحه‌بندی لیست کلاینت‌ها در خود SQLite انجام می‌شود. روی یک جدول رویداد با ۱ میلیون ردیف، داشبورد در حدود ۱ ثانیه (فقط بار اول) بالا می‌آید و بکاپ بدون تاریخچه کمتر از ۰٫۱ ثانیه است.
* بیشترین بار دیسک مربوط به خود xui-factor است (هر چند ثانیه برای هر کلاینتِ دارای مصرف، یک رویداد `traffic_applied` می‌نویسد). در سرورهای شلوغ در `/etc/xui-factor/config.json` مقدار `audit_retention` را کمتر (مثلاً `"7d"`) و `poll_interval` را بیشتر (مثلاً `"10s"`) کنید و `systemctl restart xui-factor` بزنید.
* لاگ دسترسی GET های موفق نوشته نمی‌شود تا journald بی‌دلیل روی SSD ننویسد.

## امنیت

رمز با PBKDF2-SHA256 (۲۰۰هزار دور) ذخیره می‌شود؛ نشست با کوکی امضاشده‌ی `HttpOnly`+`SameSite=Strict`(+`Secure` با SSL)؛ محافظت CSRF (هدر سفارشی + بررسی Origin)؛ محدودیت تلاش ورود (۵ خطا = ۵ دقیقه قفل)؛ CSP سخت‌گیرانه و بدون هیچ منبع خارجی (پنل کاملاً آفلاین کار می‌کند). فایل `/etc/xui-factor/panel.json` با مجوز 600 ذخیره می‌شود.

## محدودیت‌ها

* پنل وب فعلاً فقط **SQLite** را پشتیبانی می‌کند. با PostgreSQL، دستورات خود `xui-factor` کار می‌کنند ولی لیست‌های پنل نه.
* بسته‌ی همراه فقط `linux_amd64` است. برای ARM64 فایل `xui-factor_*_linux_arm64.tar.gz` را از ریلیز رسمی در پوشه‌ی `vendor/` بگذارید.
* صدور SSL به اینترنت و دسترسی پورت 80 از بیرون نیاز دارد. بخش گرفتن گواهی (acme.sh) در محیط توسعه آفلاین قابل آزمایش نبود؛ منطق آن از روش خود 3x-ui کپی شده است.
* حداقل Python 3.8 (روی Ubuntu/Debian به‌صورت پیش‌فرض هست؛ نصب‌کننده در صورت نبود نصبش می‌کند). هیچ وابستگی pip لازم نیست.

## توسعه و تست

```sh
XFP_TEST_BIN=/path/to/xui-factor python3 -m unittest discover -s tests -v   # ۷۹ تست سرتاسری با باینری واقعی
node tests/ui_smoke.js                                                      # تست رابط کاربری
```
